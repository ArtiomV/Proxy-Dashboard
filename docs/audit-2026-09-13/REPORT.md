# Аудит логики Proxy Dashboard — 13 сентября 2026

Проверены текущие локальные реализации мониторинга, HTTP, кэша, пингов,
автоперезагрузки, очистки, бэкапов, ежедневного биллинга, сопоставления счетов,
эквайринга и восстановления розничных портов; просмотрены связанные тесты.
Это целевой аудит, а не гарантия отсутствия ошибок во всём проекте.
Продовые данные, реальные платежи, запросы к серверам и сообщения клиентам
не использовались. Исправления HTTP/ИИ из предыдущего этапа сохранены;
перечисленные ниже дефекты в этом этапе не исправлялись.

P1 — исправить в первую очередь: деньги, удаление данных, доступ оплаченного
клиента. P2 — исправить следом: достоверность мониторинга и устойчивость операций.

## Подтверждено воспроизведением

### 1. P1 — оплата может навсегда остаться в paid без зачисления

Место: `src/routes/payments.js:190–211`, `src/db/card-payments.js:19–24`.

markPaid коммитит статус до atomicCredit. При временной ошибке зачисления
обработчик отвечает 500. Следующий webhook видит paid, получает changes=0
и отвечает 200 duplicate, не пытаясь зачислить деньги. Аналогичное окно есть
при остановке процесса между этими операциями. Отдельной джобы восстановления
paid → credited в просмотренных jobs/startup нет. Лог и алерт требуют ручной
работы, но не восстанавливают платёж; при аварийной остановке алерта может не быть.

Воспроизведение: первый вызов 500, второй 200 duplicate, atomicCredit вызван
только один раз, запись осталась paid. Провайдер и ошибка БД моделируются;
вызывается настоящий обработчик маршрута и настоящий SQLite-репозиторий.

Исправление: при paid без credited разрешать безопасное продолжение; запись
ledger, баланс, комиссию и credited объединить в транзакцию с уникальным
ключом события оплаты. Побочные уведомления выполнять после коммита.
Просто убрать ранний return нельзя: тогда появится риск двойного зачисления.

### 2. P1 — частичная оплата закрывает полный счёт по номеру

Место: `src/billing/bill-settle.js:48–50`.

Правило совпадения номера вызывает take без проверки remaining >= bill.amount.
Счёт на 10 000 ₽ становится paid после перевода 1 ₽, если номер есть в назначении.
При упоминании нескольких номеров могут закрыться несколько счетов сверх суммы
платежа. Это ошибка статуса счёта, не дополнительное зачисление на баланс.
Существующий тест частичной оплаты проверяет только назначение без номера.

Воспроизведение: invoice=10000, payment=1, actualStatus=paid.

Исправление: номер определяет назначение платежа, но не доказывает полную оплату;
контролировать остаток и сумму покрытия для каждого счёта. Если требуется учёт
частичных платежей — хранить отдельные распределения сумм по счетам.

### 3. P1 — неудачное восстановление прокси считается успешным

Место: `src/jobs/retail-guard.js:164–180`, условие повтора `:251–256`.
Аналогичная логика есть в legacy `src/jobs/debt-block.js:128–150`.

Ошибки setPortValidBefore логируются, но после цикла все blockedRows переводятся
в leased и долговые признаки сбрасываются. Клиент получает «сервис восстановлен»,
хотя продлить порт не удалось. Следующий цикл не заходит в восстановление, так
как больше нет blockedRows/balanceNegativeSince. Платящий клиент остаётся без
доступа; частично успешная операция имеет ту же проблему для оставшихся портов.

Воспроизведение: getConfForm возвращает ошибку недоступности; первая итерация
показывает restored=[r], статус leased, сообщение об успехе; вторая итерация
не делает повторной попытки. Все сетевые вызовы заменены локальной имитацией.

Исправление: фиксировать успешность отдельно по портам; оставлять неуспешные
операции pending/blocked для повтора. Очищать общий долговой след и сообщать
полный успех только после подтверждения всех требуемых продлений.

### 4. P1 — retention удаляет данные недоступного сервера

Место: `src/jobs/cleanup.js:55–59, 74–76, 84–89`.

Сервер со старым кэшем попадает в skippedSrv и не добавляет свои порты в liveIds.
Но при удалении skippedSrv не используется: отсутствие в liveIds трактуется
как исчезнувший порт. Достаточно одного другого сервера со свежим кэшем, чтобы
снять общий guard. Удаляются все daily_traffic записи такого порта, если его
последняя дата старше retention_stale_ports_days (по умолчанию 3 дня), а также
его история в памяти. Это может удалить данные раньше общего retention 90 дней.

Воспроизведение: свежий S1 и устаревший S4; запись S4 пятидневной давности удалена
из SQLite и памяти, хотя результат одновременно содержит skippedSrv=[S4].

Исправление: удалять только в пределах серверов, для которых есть авторитетный
свежий набор портов; серверы без кэша и с ошибкой/устаревшим кэшем сохранять.
Пропажа из bandwidth feed сама по себе также требует сверки с list_ports_json.

### 5. P2 — протухшие пинги продолжают становиться кандидатами на reboot

Место: `src/jobs/modem-ping.js:98–106`,
потребители `src/services/proxy-issues.js:19–38`, `src/jobs/auto-reboot.js:33–34`.

Проверка fresh отключает только непосредственные ping-алерты. Строка уже
записана в modem_ping с текущим ts, без признака недостоверности. Агрегатор
computeProxyIssues учитывает её, как свежий замер, и передаёт автоперезагрузке.
ИИ-отчёт и публичная статистика читают ту же историю без информации о fresh.

Воспроизведение: 66 одинаковых ответов за 65 минут; последние 60 минут уже
признаны stale внутри ping job, но computeProxyIssues всё равно выдаёт 100%
потерь и кандидата. При включённом auto_reboot_enabled это может инициировать
перезагрузку по данным, которые сама система объявила недостоверными.

Исправление: хранить/передавать валидность и время самого замера; одинаково
исключать stale во всех потребителях, особенно в автоматических действиях.
Нельзя считать равенство строки надёжным доказательством остановки измерений:
постоянные 100% потерь или одинаковая задержка тоже могут быть настоящими.

### 6. P2 — пропавший ping_stats оставляет старый результат свежим

Место: `src/jobs/modem-ping.js:47–51, 95–96`, отображение `latest():55–60`.

При пустом/неразбираемом ping_stats выполняется continue, без инвалидирования
предыдущего st.last. alive проверяет лишь сохранённый флаг fresh, а не возраст ts.
Последний успешный или неуспешный результат может оставаться авторитетным
неограниченно долго, пока модем присутствует в API без корректного ping_stats.

Воспроизведение: успешный замер 24 часа назад, сейчас пустой ping_stats;
alive=true и fresh=true. Так же может застрять false после старой ошибки.

Исправление: инвалидировать результат при отсутствующем/некорректном замере;
применять TTL к чтению alive/latest и ко всем потребителям статуса.

### 7. P2 — среднесуточный расход занижен: шесть дней делятся на семь

Место: `src/services/port-validity.js:54–62`.

from=today-7, фильтр date > from и date < today включает только today-6…today-1.
Деление идёт на семь. При ежедневных списаниях по 100 ₽ функция возвращает
85,71 ₽ вместо 100 ₽. Она используется для срока продления после оплаты и
предупреждений о балансе: запас дней оказывается завышен.

Исправление: включить нижнюю границу date >= from, сохранив исключение today.
Добавить тест с отдельным списанием ровно на нижней границе окна.

### 8. P2 — ошибка сжатия оставляет испорченный архив под окончательным именем

Место: `src/jobs/backup.js:145–160`.

createWriteStream открывает dest+'.gz' сразу с усечением. При ошибке чтения,
сжатия или записи нет атомарной публикации и уборки всех потоков. Остаётся
пустой/неполный .gz; при повторе в тот же день существующий архив уже затёрт.
Поиск последней копии в backup-test выбирает архив по имени, не по успешности
его создания; более старый исправный архив автоматически не подбирается.

Воспроизведение: уже существующий архив 16 байт и ошибка открытия исходного
файла — Promise rejected, прежний архив стал 0 байт. Пропажа источника здесь
служит инъекцией ошибки; тот же неатомарный способ публикации используется
при более обычных отказах записи/ENOSPC. Не утверждается, что это уже случилось
с реальными бэкапами.

Исправление: pipeline с обработкой ошибок, уникальный временный файл,
проверка результата, rename поверх окончательного пути только после успеха;
при отказе удалять только временный файл, сохраняя предыдущую копию.

## Дополнительные замечания по статическому обзору

- Два независимых правила хранения: runRetentionCleanup учитывает настройки,
  а runHistoryPrune безусловно удаляет rotation_log/system_log/proxy_checks
  старше 60 дней. Выставленные 90–365 дней для этих таблиц не соблюдаются.
  Нужен один источник retention. См. `src/jobs/backup.js:71–86` и
  `src/jobs/cleanup.js:124–131`.
- Клиентский инструмент check_proxy после двух HTTP-отказов возвращает
  working=true, если просто открылось TCP-соединение. Закрывает это статусом 0
  и пояснением про открытый порт, но булев признак «работает» вводит в заблуждение:
  неверный пароль или неработающий upstream этому не мешают.
  См. `src/routes/proxy-checks.js:81–98`. Разделить port_open и http_working.
- HTTP выбирает первый действующий порт по IMEI, а история подписана nick.
  При нескольких модемах с одним IMEI оба ника проверят один и тот же порт.
  На S4 клонированные IMEI документированы; конкретные текущие соответствия
  требуют live-сверки. Не доказано, что это причина исходного отчёта.
- Биллинг аренды считает текущие записи bandwidth feed, хотя списывает за вчера;
  резервный COUNT(DISTINCT nick) не включает server_name и срабатывает только
  при полном нуле modemCount. Частично недоступный парк может дать неполное
  число; исправление требует уточнения политики «порт или физический модем»
  и исторических назначений, поэтому не включено в подтверждённые дефекты.
- Ротация logs/dashboard.log и план очистки описаны в соседнем
  `docs/HTTP-AND-DISK-AUDIT-2026-09-13.md`; созданный logrotate-конфиг на прод
  не установлен. Реальный объём освобождения неизвестен без инвентаризации.

## Как воспроизвести

Из корня проекта:

```sh
node docs/audit-2026-09-13/reproduce.cjs
```

Нужны уже установленные зависимости проекта. Сценарий использует SQLite
в памяти, собственный временный каталог и подменённые внешние зависимости.
Не запускает приложение/cron, не слушает сетевые порты, не отправляет запросы
провайдеру и не пишет рабочие данные. results.json — сохранённый вывод.

Все 8 диагностических сценариев завершились успешно (exit 0), то есть
подтвердили перечисленное текущее неправильное поведение. Это не regression
тесты ожидаемого исправленного поведения: после исправлений их проверки нужно
заменить проверками корректного результата в штатном tests/.

Штатный полный набор из предыдущего этапа прошёл (914 тестов; после него
дополнительный TLS-сценарий проверен отдельно). Прохождение набора не опровергает
найденные проблемы: эти сочетания условий в существующих тестах не покрыты.
В этом этапе производственный код не изменялся и полный набор не повторялся.
