# HTTP-проверки и освобождение диска — 13 сентября 2026

Проверен локальный код HTTP-транспорта, выбора портов, API-кэша, пингов,
ИИ-сводки, retention, watchdog, бэкапов, логирования и deploy-скрипта.
Продовые БД, логи и заполнение дисков не исследованы; точная причина отказов
перечисленных модемов пока не установлена. Это целевой обзор связанных модулей,
не полный аудит биллинга, безопасности и всех маршрутов приложения.

## Что означает HTTP-сбой

Путь: дашборд → publicIp сервера → первый действующий клиентский HTTP-порт
из ports[IMEI] → Basic auth → CONNECT → TLS → настроенный сайт.
Пинг берётся из net_details.ping_stats ProxySmart. Успешный пинг не проверяет
доступность внешнего порта, авторизацию, DNS целевого сайта, TLS или фильтрацию.

Почему затронута только часть модемов:

- 407/CONNECT 407: реквизиты, политика доступа или ограничение исходного IP;
- ECONNREFUSED: конкретный порт не слушает либо не проброшен;
- timeout: маршрут/фильтрация, зависший порт, DNS upstream, совпадение с ротацией;
- CONNECT 502/503: прокси не смог установить туннель; требуется его серверный лог;
- 403/429: ограничения сайта для выходного IP, не доказательство поломки модема;
- content_mismatch: иной ответ сайта/редирект/заглушка; до исправления — также
  артефакт ручного разбора chunked;
- ошибка сертификата: цепочка доверия, имя, срок действия или TLS-перехват.

Это направления диагностики, не установленная причина данного инцидента.
HTTP 500 API ProxySmart отдельно от HTTP-ответа сайта. Номер модема не доказывает
общий USB-хаб. В присланном ИИ-тексте перечислены 11 модемов S4 при заявленных 10,
а MD2_48 продублирован. Перезапуск всей группы по такому анализу не обоснован.

## Исправлено локально

- Общий дедлайн TCP/CONNECT/TLS/ответа; прежний inactivity timeout мог постоянно
  продлеваться поступающими байтами, блокируя Promise.all и следующие запуски.
- Node HTTP parser также внутри TLS: декодирование chunked, обработка оборванного
  ответа, ограничение тела ровно первыми 512 KiB с завершением Promise.
- CONNECT использует порт URL, а не безусловно 443.
- Ресурсы закрываются при завершении/ошибке; проверка TLS-сертификата включена
  (ранее rejectUnauthorized:false скрывал ошибки доверия/перехват).
- ИИ получает группировку реальных ошибок; инструкции отделяют гипотезы от фактов.

Редиректы 200–399 по-прежнему считаются допустимыми без перехода по Location.
Если нужен конечный документ после редиректа, это отдельное изменение политики
с ограничением переходов и повторной проверкой адресов. В текущей конфигурации
лучше использовать стабильный небольшой HTTPS endpoint с ожидаемым содержимым.

## Что проверить на проде первым

1. В modem_httpcheck сгруппировать за нужный день server/nick/error/status, отдельно
   посмотреть время и последние успешные проверки. Пропуски offline и
   no_valid_client_credentials не считать HTTP-сбоями (код уже это делает).
2. Сверить выбранный порт с актуальным list_ports_json, клиентом и ником. Есть
   документированные клонированные IMEI на S4; выбор только по IMEI требует
   проверки на живых данных. Не угадывать привязку по номеру модема.
3. Проверить тот же URL через тот же порт с хоста дашборда; сопоставить с запросом
   клиента. Реквизиты не писать в логи, аргументы команд или отчёт.
4. Сравнить ошибки со временем ротаций, логами прокси и ограничениями доступа.
   Второй независимый небольшой URL поможет отделить отказ сайта от отказа порта.
5. После выкладки учитывать новые TLS-ошибки: они раньше скрывались. Исправлять
   цепочку доверия/endpoint, а не возвращать глобальное отключение проверки.

## Диск: найденное в коде

- disk_low_warn проверяет раздел приложения: это не алерт о диске S4/S3.
  Второй watchdog проверяет раздел бэкапов (либо /) и порог 500 MB; проверки
  сейчас покрывают разные пути и имеют разные пороги.
- src/logger.js бесконечно дописывает logs/dashboard.log. pm2-logrotate управляет
  логами PM2; отдельная ротация файла приложения в репозитории отсутствовала.
- Бэкапы уже сжимаются: дневные удаляются по порогу 7 дней, monthly — 12 файлов,
  pre-deploy — последние 2 каталога. Удаление дневных идёт после успешного нового
  бэкапа: при полном диске до этой стадии можно никогда не дойти.
- gzipFile пишет сразу в окончательный .gz; при ошибке остаётся частичный архив.
  Нужны pipeline, временный файл, атомарное переименование после успеха и очистка
  временного файла при ошибке. Без этого имя .gz не гарантирует пригодность копии.
- DELETE старых строк SQLite обычно освобождает страницы для повторного
  использования внутри БД, но не уменьшает файл на диске. Нельзя удалять WAL/SHM
  вручную; VACUUM при нехватке места может потребовать дополнительное место.
- cleanupStalePortMappings собирает skippedSrv, но не исключает такие серверы
  из удаления daily_traffic. Комментарий обещает защиту недоступных серверов,
  реализация её не обеспечивает. Это отдельная ошибка retention, требующая
  регрессии с одним свежим и одним недоступным сервером перед изменением.

## Проект автоматической очистки

Первый готовый компонент: config/logrotate/proxy-dashboard. Порог 50 MiB,
14 архивов, сжатие, хранение до 14 дней. Нужен запуск logrotate каждый час;
обычный ежедневный запуск не ограничивает рост в течение дня. copytruncate
совместим с открытым WriteStream, но допускает потерю нескольких строк в момент
копирования и временно требует места под копию. Долгосрочно лучше ротация
с переоткрытием потока или единый stdout → PM2 с одним владельцем логирования.
Конфигурация не установлена на сервер.

Следующий компонент — отдельная DiskMaintenance job:

1. Каждые 60 минут: измерять фактические разделы приложения, БД и бэкапов,
   свободные байты и inode; объединять одинаковые разделы. Сканировать только
   явно разрешённые каталоги, без рекурсивного обхода всей системы.
2. Первые 24 часа dry-run: отчёт размеров по категориям и список кандидатов
   с причиной/возрастом. Затем включение только правил из таблицы ниже.
3. Единая блокировка с backup/restore-test/deploy; активные операции исключать.
   Проверять lstat, не переходить по symlink, повторно сверять inode/размер/mtime
   перед удалением. Файлы вне разрешённого корня никогда не удалять.
4. Запускаться и при нормальном свободном месте — это предупреждает заполнение.
   При <20% или <2 GiB выполнять разрешённую очистку раньше; после неё повторно
   измерить место. При <10% или <500 MiB либо недостаточном освобождении — алерт
   с причиной и крупнейшими категориями; не расширять автоматически список удаления.
5. Писать аудит: правило, число файлов, байты до/после, ошибки; ограничить один
   проход, например 100 файлов / 1 GiB. Никакого рекурсивного rm по маске.

| Категория | Политика |
|---|---|
| Архивы dashboard.log | Только logrotate, один владелец удаления |
| backup-test-<timestamp>.db/.db.gz и sidecars в выделенном tmp | Старше 48 ч, нет активного restore-test; только обычные файлы |
| Частичные gzip | После внедрения суффикса .partial: старше 48 ч, нет активного backup |
| Дневные копии | Старше 7 дней; сохранять минимум 2 проверенные копии; удалять независимо от успеха сегодняшней операции, только после проверки сохранённых |
| Monthly | 12 разных месяцев, проверенные копии; .db/.gz одного месяца не считать двумя месяцами |
| Pre-deploy | Последние 2 успешных снапшота; удаление только после подтверждения нового и под общей блокировкой |
| SQLite telemetry | Существующий retention; единая политика вместо дублирующих retention/HistoryPrune |
| Неизвестные файлы | Только отчёт, без удаления |

Всегда сохранять рабочую БД, WAL/SHM, клиентские/финансовые данные, конфигурации,
сертификаты и JSON состояния из OPERATIONS.md. Не чистить общий /tmp, Docker,
системный journal или кэши пакетов без отдельной инвентаризации владельца.

Перед включением job нужны тесты: symlink/path escape, активная операция,
последние резервные копии, неуспех нового бэкапа, ошибки удаления, одинаковый
раздел у нескольких путей, повторный запуск, отсутствие файлов и dry-run.
Для оценки реально освобождаемых гигабайтов сначала нужна инвентаризация продового
диска; процент алерта сам по себе не указывает, какие файлы занимают место.
