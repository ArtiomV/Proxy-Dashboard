## Что остаётся по нашему продукту

### P0 — перед эксплуатацией

1. **Развернуть адаптер публичной status-страницы.** В Dashboard готов реальный `GET /api/public/status` и drop-in `integrations/arendaproxy/statuses.js`, но репозитория сайта arendaproxy.ru здесь нет. Пока его `/js/statuses.js` не заменён, публичная страница продолжит показывать статические 100%.
2. **Мониторинг самого мониторинга.** Нужен внешний независимый heartbeat из другой площадки: Dashboard/ProxySmart/API/Telegram могут упасть вместе, и внутренняя проверка этого не увидит.
3. **Проверить прод-пороги после накопления `modem_ping`.** Нужны 7–14 дней реальных baseline-данных до окончательного включения агрессивного failover по потере связи.
4. **Доставка алертов.** Добавить контроль «Telegram не доставляет» с резервным каналом, а не только проверять, что событие создано локально.

### P1 — следующий практичный этап

1. **Полный жизненный цикл инцидента:** open → acknowledged → investigating → resolved, владелец, комментарий, таймлайн, MTTA/MTTR, связь с публичным статусом.
2. **Граф зависимостей и root cause:** площадка → сервер → USB-hub → модем → клиентский порт. Сейчас есть только важная, но одноуровневая зависимость сервер → модем.
3. **Эскалации и расписания дежурств:** повтор через N минут, повышение приоритета, второй получатель/канал, тишина по расписанию.
4. **Плановые SLA-отчёты:** автоматическая рассылка PDF/HTML/CSV по расписанию и отчёт по клиенту, а не только ручное открытие/экспорт.
5. **Сроки SIM-контрактов:** дата уже хранится и редактируется; остаётся добавить предупреждения за 30/14/7 дней и список предстоящих продлений.
6. **Status page incidents:** реальные компоненты готовы, но нужны сообщения об инциденте/работах, история и подписки пользователей.

### P2 — зрелость и масштабирование

1. Автообнаружение новых серверов/модемов и применение шаблонов мониторинга.
2. Динамические baseline и anomaly detection по задержке, потерям, трафику, CPU/RAM/диску; прогноз исчерпания ресурсов/пакетов.
3. Инвентаризация и контроль изменений конфигурации ProxySmart/APN/портов/прошивок.
4. Раздельные роли и видимость мониторинга по сотрудникам/клиентам.
5. Несколько независимых collectors/probes для разных площадок и сравнение результатов.

## Сравнение с PRTG

PRTG шире не отдельным графиком, а платформенными возможностями: auto-discovery и библиотекой sensor templates; удалёнными probes и централизованным multi-site мониторингом; картами/зависимостями; расписаниями, эскалациями и несколькими каналами уведомлений; плановыми отчётами; SNMP/WMI/SSH/HTTP/API, flow-протоколами и packet sniffing; мониторингом виртуализации, облаков, приложений и БД.

Для нашего прокси-сервиса не нужно копировать все enterprise-сенсоры. Наибольшая отдача будет от независимого remote probe, incident lifecycle/root cause, эскалаций и плановых SLA-отчётов. NetFlow/sFlow/IPFIX, VoIP, широкий WMI/SNMP-каталог и enterprise cluster нужны только при росте инфраструктуры и не являются P0.
