# FIX-SPEC: плановые (повторяющиеся) расходы recurring_costs

**Дата аудита:** 2026-09-17
**Объект:** рефакторинг повторения операций (миграция `090_recurring_costs.sql`, `src/billing/recurring-costs.js`, роуты `src/routes/billing-ext.js`, фронт `public/js/admin/finance.js`).
**Метод:** независимый код-ревью + перепроверка ключевых находок по исходникам.
**Итог:** 2 critical, 7 major, 12 minor. Все дефекты C1–M7, m1–m8 исправлены и покрыты регрессионными тестами (`tests/api/recurring-costs.test.js`: 10 → 19 тестов; полный suite 141 файл / 949 тестов — зелёный). Открытые pre-existing пункты — в разделе 4.

Маркеры severity: **C** — потеря/порча финансовых данных или переписывание истории; **M** — неверные цифры на экране / потеря полей / двойной учёт; **m** — UX и гигиена.

## 1. Critical

### C1 · DELETE «оживляет» завершённое правило задним числом · статус: ИСПРАВЛЕНО

**Воспроизведение.** Правило `start=2024-01, end=2024-12` (давно завершено). UI рисует кнопку «Остановить» для всех правил из `recurring.all`, включая завершённые. `DELETE /api/admin/recurring_costs/:id` безусловно ставил `end_period = текущий месяц` → диапазон расширялся, правило ретроактивно добавляло расходы в дашборды всех месяцев между старым концом и «сейчас». Тот же баг при повторном stop в другом месяце (stop в июне → повторный DELETE в сентябре «оживлял» июль–август).

**Корневая причина.** stop-ветка не читала существующий `end_period` (SELECT только `id, start_period`) и не проверяла состояние «уже завершено».

**Требуемое исправление.**
1. SELECT читает также `end_period`.
2. Если `end_period <= текущий месяц (МСК)` — no-op, ответ `{ ok: true, alreadyStopped: true }`, без UPDATE.
3. Опциональный параметр `end=YYYY-MM` (query или body): явный месяц окончания; валидация формата и `end >= start_period`, иначе 400.
4. Параметр `hard=1`: физическое удаление, только для завершённых (`end_period < cur`) или будущих (`start_period > cur`) правил; иначе 409 с пояснением.
5. UI: завершённым правилам — бейдж «завершено» + кнопка «Удалить» (`hard=1`) вместо «Остановить»; инпут суммы disabled.

**Приёмка.** Тесты: DELETE на завершённом правиле → `alreadyStopped`, `end_period` не изменился; stop → сдвиг месяца → повторный DELETE = no-op; `end` явный; `hard=1` на завершённом удаляет, на действующем → 409; `end < start` → 400.

### C2 · Stop от реального «сейчас» при просмотре прошлого месяца · статус: ИСПРАВЛЕНО

**Воспроизведение.** Админ листает дашборд на прошлый месяц, открывает модалку затрат, жмёт «Остановить» — backend ставил `end_period = реальный текущий месяц`; правило продолжало действовать в просматриваемом периоде, модалка после перезагрузки показывала его активным. Confirm-текст «до конца текущего месяца» не уточнял, какого.

**Исправление.** Confirm-текст зависит от состояния: будущее правило — «будет удалено полностью»; действующее — «будет действовать до конца {YYYY-MM по МСК} включительно». Текущий месяц на фронте считается по МСК (`_finCurMskMonth()`).

**Приёмка.** Ручная: кнопка и текст соответствуют состоянию правила (будущее/действующее/завершённое).

## 2. Major

### M1 · «Итого за месяц» модалки не включал плановые правила · ИСПРАВЛЕНО

**Суть.** `_finCostsRecalc` суммировал только `.set-row[data-cat]` + `[data-auto-amount]`; строки правил (`fcm-rule-row`) ни в какой тотал не попадали. При затратах только из правил модалка показывала итог ≈ SIM-пакеты, а KPI дашборда — полную сумму.

**Исправление.** В сводку добавлен блок «Плановые» (`fcPlanTotal`). `planRub` = сумма активных в периоде правил (`data-active="1"`, конвертация по тем же курсам), исключая правила, перекрытые введённым значением > 0 в разовой секции с тем же `cat|key`. `Итого = ручные + SIM + плановые`. Пустой инпут с placeholder=plan двойного счёта не даёт.

**Приёмка.** Ручная: месяц только с правилами — «Плановые» и «Итого» совпадают с KPI дашборда; ввод override уменьшает «Плановые» и увеличивает «Ручные» на ту же позицию.

### M2 · PUT из UI молча затирал qty · ИСПРАВЛЕНО

**Суть.** `saveRecurringRule` не слал `qty` → валидатор нормализовал в `null` → UPDATE затирал qty у sim-правил из бэкфилла.

**Исправление.** Фронт: `data-qty` на строке правила, qty шлётся в body. Бэк: PUT при `qty === undefined` сохраняет существующее значение (existing читается полностью).

**Приёмка.** Тест: PUT без поля qty → qty сохранено, amount обновлён.

### M3 · Subkey нового правила — свободный текст · ИСПРАВЛЕНО

**Суть.** Для perItem-категорий (server/electricity/hosting/salary) subkey, не совпадающий с ключом локации, ломал подсказку «по плану», не перекрывался разовой строкой месяца (двойной учёт в effective) и обходил overlap-проверку при другом написании.

**Исправление.** В форме добавления для perItem-категорий — `<select>` из `meta.locations` + «(общая)» = null; для `other` subkey всегда null. Переключение по change селекта категории.

### M4 · Бэкфилл миграции · ИСПРАВЛЕНО (частично — см. открытые вопросы)

**Суть.** `090_recurring_costs.sql` копирует весь последний заполненный месяц в бессрочные правила, не отличая разовые траты; при дубликатах (category, subkey) в resolve побеждала произвольная строка.

**Исправление.** К notes добавляется маркер `[миграция: проверьте]`; детерминированный tie-breaker `ORDER BY category, subkey, id` в `resolveMonthlyCosts` и `listAllRules`.

**Приёмка.** Тест: ручной `db.exec` SQL миграции — правила только из последнего месяца, notes с маркером, повторный exec не дублирует.

**Открытый остаток.** Семантически миграция не может отличить разовую трату от повторяющейся — оператор обязан просмотреть правила с маркером после деплоя (см. раздел 5, runbook).

### M5 · Сохранение месяца затирало override-строки, не отрисованные в модалке · ИСПРАВЛЕНО

**Суть.** POST monthly_costs = wipe+insert; строки месяца, не попавшие в DOM (несматчившийся subkey, второй 'other'), стирались сохранением без ведома пользователя.

**Исправление.** При рендере собирается `renderedKeys`; неотрисованные строки показываются блоком «Другие строки этого месяца» в секции «Прочее» и уезжают в POST как обычные строки.

### M6 · CRUD правила терял несохранённые суммы месяца · ИСПРАВЛЕНО

**Суть.** После save/stop/add правила вызывался `openFinanceCostsModal()` — полная перерисовка, все несохранённые инпуты месяца терялись.

**Исправление.** HTML блока правил вынесен в `_buildRulesHtml`; после CRUD перезапрашивается GET и заменяется только `.fcm-rule-list` + `_finCostsRecalc`; инпуты `.set-row` не трогаются.

### M7 · UTC вместо МСК на границе месяца · ИСПРАВЛЕНО

**Суть.** `currentPeriod()` и дефолтные period считались через `toISOString()` (UTC); в 00:00–02:59 МСК первого числа stop ставил `end_period` = прошлый месяц, а модалка/дашборд показывали прошлый месяц как текущий. Конвенция проекта — МСК (`getMoscowToday`).

**Исправление.** `currentPeriod()` — МСК (`Europe/Moscow`); дефолтный period в GET monthly_costs и finance_dashboard — от `getMoscowToday().slice(0,7)`.

## 4. Открытые пункты (pre-existing, вне рефакторинга)

### O1 · Расхождение пересчёта валют модалка vs сервер при недоступном курсе · ОТКРЫТО (v2.10.8)

Модалка при отсутствии курса считает MDL/RON-вклад = 0 (`rate[cur]||0`), серверный `fx.toRub` при `rate=null` возвращает сумму как есть — тоталы расходятся.
**Предлагаемый фикс:** единая политика «нет курса → позиция исключается из итога + предупреждение», реализованная один раз на сервере; фронт только отображает.
**Приёмка:** при недоступном ЦБ и пустом ручном фиксе модалка и дашборд показывают одинаковый итог; предупреждение видно в обоих местах.

### O2 · `created_at`/`updated_at` в UTC · ОТКРЫТО (общая конвенция всех таблиц)

`datetime('now')` пишет UTC при MSK-конвенции проекта. Трогать точечно одну таблицу нельзя — нужен проектный подход (миграция формата или явный сдвиг в SELECT). Вынести в отдельную задачу.

## 5. Runbook при деплое

1. Миграция `090` применится раннером автоматически; бэкфилл сработает только если `recurring_costs` пуста и `monthly_costs` не пуста (в текущей production-копии monthly_costs пуста — бэкфилл будет no-op).
2. Если бэкфилл сработал — открыть «Финансы → Затраты → Плановые операции» и просмотреть все правила с пометкой `[миграция: проверьте]`: разовые траты последнего месяца остановить/удалить.
3. Глазами проверить модалку: блок «Плановые» в сводке, секция правил, подсказки «по плану …», сохранение разовых сумм не трогает правила.
